04
Staging → Commit → Push
변경사항을 저장하고, 원격 저장소로 올려서 GitHub 화면에서 확인해요.
🖐️

초대 수락 → Clone → 파일 수정 → Commit → Push까지 직접 해보세요.

자주 만나는 문제들

✓Commit 버튼이 안 눌러져요 → 파일을 먼저 체크박스로 Stage 해야, Commit할 수 있어요.
✓Commit했는데 GitHub엔 안 보여요 → Commit은 내 컴퓨터에만 저장돼요. Push까지 눌러야 다른 사람도 볼 수 있어요.
✓Push가 안 돼요 → Collaborator 초대를 아직 수락 안 했을 수 있어요. 이메일 · 알림함을 다시 확인해요.
✓Push할 때 로그인이 거부돼요 → 비밀번호가 아니라 PAT(Personal Access Token)을 입력해야 해요. 만료됐다면 새로 발급받아요.
✓Push가 막히고 충돌(Conflict)이 나요 → 같은 파일을 동시에 고쳤을 때예요. Pull로 최신 내용을 받아, 겹친 부분을 정리하고 다시 Commit해요.
PART 3 · 기획

이제.... 만들어볼까요?

수도 코드 ( Pseudo code )
기획과 개발을 잇는, 첫 번째 언어예요.

수도 코드 ( Pseudo code )란 무엇일까요?

01
정의
실제 프로그래밍 언어가 아닌 사람의 일반적인 언어로 로직의 흐름을 만드는 것.
02
특징
if, else 같은 영어 키워드도 몰라도 돼요 — "~라면", "~하지 않으면"처럼, 평소 쓰는 말 그대로 적으면 돼요.
03
형식은 자유
정해진 규칙은 없어요 — 우리 팀이 알아볼 수 있으면 충분해요.
04
목적
코드를 짜기 전에, 그 로직이 말이 되는지부터 먼저 확인하는 것.

왜 수도 코드부터 쓸까요?

01
팀 커뮤니케이션
기획자와 개발자가 프로그래밍 언어 없이도 로직을 함께 검토할 수 있어요.
02
로직을 먼저 검증
문법 오류에 발목 잡히지 않고, "이 순서가 맞나?"부터 확인할 수 있어요.
03
언어에 얽매이지 않음
C#이든 Python이든, 수도 코드는 거의 그대로 옮겨 쓸 수 있어요.
04
버그를 미리 잡기
코드로 옮기기 전에, 빠뜨린 예외 상황("안 되는 경우엔?")을 먼저 찾아낼 수 있어요.
코드에서 발생하는 버그가 아니라, 논리적인 기획 오류를 찾아야 해요.

그 도어를, 수도 코드로 적어볼까요?

그냥 말로 자연어
01
플레이어가 문을 밀어 연다.
02
문이 열리는 방향이 미는 방향과 같으면, 문이 열린다.
03
문이 열리는 방향이 반대라면, 문은 열리지 않고 부딪히는 소리만 난다.
TIP
문장은 자연스럽지만, "조건" / "동작" 구분이 안되죠?
줄 바꿔서 정리 여전히 자연어
(event) 플레이어가 문을 밀어 연다. 문이 열리는 방향과 미는 방향이 같다면, → 문이 열린다. 문이 열리는 방향과 미는 방향이 반대라면, → 문은 열리지 않고, 부딪히는 소리를 낸다
TIP
if, else 없이도 조건 구분이 되
인스윙/아웃스윙, 그 방향 하나가 이 로직의 핵심 조건이에요.

좋은 수도 코드.

✓이벤트가 시작하면 좋을 것 같아요 — "플레이어가 문을 연다", "화면을 터치한다"처럼 명확하게.
✓조건을 분명하게 "~라면 / ~이 아니면" 처럼 나눠주세요 — 복잡한 건 괜찮지만, 명확하지 않으면 안돼요.
✓가능하면 복합적인 내용은 지양.! — 복잡해지는 것은 문장을 분리해보세요.
✓예외 상황도 꼭 적으세요 — "안 되는 경우엔?"을 먼저 생각하는 습관.
✓들여쓰기로 구조를 보여주세요 — 조건 안에 조건이 있으면, 한 칸씩 밀어서.
아.. 이러니 파이썬 얘기하는 것 같네..
🔁

예외 상황까지 포함해서 적어보세요.
스크립트 문법은 몰라도 괜찮아요 — 우리말 문장으로 충분해요.

PART 4 · 엔진

말로 적은 로직을,
이제 코드로 옮겨볼까요?

수도 코드가 실제 스크립트가 되는 과정을, 씬 전환 예제로 그대로 따라가봅시다.

MonoBehaviour, 정리해봐요

01
정의
유니티가 기본으로 제공하는 클래스예요 — 이걸 상속해야, 게임 오브젝트에 붙는 "스크립트"가 돼요.
02
코드 vs 스크립트
코드는 프로그래밍 언어로 적은 모든 명령을 통칭하는 말.
스크립트는 그 중에서, 엔진같은 특정 프레임워크 안에서 정해진 생명주기를 따라 실행되는 코드예요.
03
결국 하나의 Component
MonoBehaviour 도 지난 주 배운 Component 중 하나예요.
Unity 가 미리 만들어준.!
04
구조
MonoBehaviour < Behaviour < Component < Object 순서로 상속을 받아요.

생명주기(Lifecycle) 메서드들

MonoBehaviour 생명주기
public class Example : MonoBehaviour { void Awake() { // 생성 직후, 딱 한 번 } void OnEnable() { // 활성화될 때마다 } void Start() { // 첫 프레임 직전, 딱 한 번 } void Update() { // 매 프레임 } void LateUpdate() { // Update가 끝난 뒤, 매 프레임 } void FixedUpdate() { // 물리 연산용. 고정 프레임 } void OnDisable() { // 비활성화될 때 } void OnDestroy() { // 파괴되기 직전, 딱 한 번 } }
참고로, Animator의 State에 붙이는 StateMachineBehaviour는 이것과는 또 다른 생명주기(OnStateEnter / OnStateUpdate / OnStateExit 등)를 가져요.

생성 · 유지 · 소멸, 3단으로 보면

🌱
생성 · 한 번
1. Awake
↓
2. OnEnable
↓
3. Start
순서대로, 딱 한 번씩.
→
🔁
유지 · 반복
1. FixedUpdate
↓
2. Update
↓
3. LateUpdate
이 순서로, 매 프레임 반복.
→
🍂
소멸 · 한 번
1. OnDisable
↓
2. OnDestroy
순서대로, 딱 한 번씩.
오브젝트가 껐다 켜지길 반복하면, OnEnable ↔ OnDisable 사이만 여러 번 오갈 수도 있어요.
완전히 사라질 때만, 마지막으로 OnDestroy가 딱 한 번 불려요.

자, 진짜 코드가 됐어요

수도 코드 복습
씬이 시작되면, → 그 씬의 프로세스를 시작한다 프로세스가 진행 중이라면, → 화면을 터치해도, 아무 행동도 하지 않는다 화면을 터치했을 때, 지금 Title 씬이라면 → Lobby 씬 로딩을 시작한다 지금 Lobby 씬이라면 → Play 씬 로딩을 시작한다 그 외의 경우라면 → Title 씬 로딩을 시작한다

public class MenuManager : MonoBehaviour { void Update() { if (Input.GetMouseButtonDown(0)) NextScene(); } void NextScene() => SceneManager.LoadScene(SceneManager.GetActiveScene().name switch { "Title" => "Lobby", "Lobby" => "Play", _ => "Title" }); }

싱글턴 패턴이란?

01
정의
프로그램 전체에서, 어떤 클래스의 인스턴스가 딱 하나만 존재하도록 보장하는 디자인 패턴이에요.
02
비유하면
우리 주임 교수님은 한 명뿐이죠.
누가, 언제 찾아가든, 결국 같은 한 사람이에요.
03
왜 Manager Class 에 어울릴까
App 에서 유일한 정보와 기능을 담당하는 Manager!
GameManager / ResourceManager / NetworkManager 등.
04
핵심은!
static 변수(Instance)로 어디서든 접근할 수 있고,
DontDestroyOnLoad로 씬이 바뀌어도 안 사라지게.

싱글턴, 코드로 보면

MenuManager.cs Singleton
public class MenuManager : MonoBehaviour { public static MenuManager Instance { get; private set; } void Awake() { if (Instance != null && Instance != this) { Destroy(gameObject); return; } Instance = this; DontDestroyOnLoad(gameObject); } }
✓static Instance — 클래스 자체에 붙는 변수라, 오브젝트 없이도 MenuManager.Instance로 바로 접근돼요.
✓이미 하나 있으면 새로 생긴 쪽을 파괴 — 씬이 다시 로드돼도 두 개가 되지 않게.
✓DontDestroyOnLoad — 씬이 바뀌어도, 이 오브젝트만은 파괴하지 말라는 함수예요.
✓이제 어디서든 MenuManager.Instance.무언가() 로 호출할 수 있어요.

그 밖에도, 디자인 패턴들

01
Observer (옵저버)
상태가 바뀌면, 관심있는 대상들에게 자동으로 알려주는 패턴이에요.
02
Object Pool (오브젝트 풀)
총알처럼 자주 생기고 사라지는 걸, 미리 만들어두고 재사용하는 패턴이에요.
03
State Machine (상태 머신)
캐릭터의 상태(대기·공격·사망 등)를 명확히 나누고, 전환을 관리하는 패턴이에요.
04
Factory (팩토리)
오브젝트를 "어떻게 만들지"를 한 곳에 몰아서 관리하는 패턴이에요.
오늘은 이름만 알아두는 정도로 충분해요 — 프로젝트가 커질수록, 하나씩 필요해질 거예요.

이 것들을 해봐요

01
진짜 우리 것으로
오늘 씬 전환으로 연습했으니, 우리 팀의 씬 구성을 고민하고 정리해서, 씬 전환을 담당하는 매니저 클래스를 만들어봐요 — 조건과 예외까지 빠짐없이.
02
Singleton 완성하기
중복된 처리를 하지 않아야 하니..! Instance + DontDestroyOnLoad까지 적용해서, 씬 전환을 담당하는 매니저 클래스를 만들어봐요.
03
HandsOnPractice 저장소 참고
조금 더 다듬어진 버전을 올려놓았으니, 열어보고 우리 코드와 비교해봐요.
04

커밋 메시지도 신경 써서 — "무엇을, 왜 바꿨는지".
