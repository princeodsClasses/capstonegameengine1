PART 2 · 기획

먼저, UI부터
짚고 갈까요?

User Interface — 들어는 봤지만, 제대로 정의해본 적 있어요?

UI, 란?

UIUser Interface
사용자와 시스템이 상호작용을 위해 소통하는 장치.
CUI
Command Line User Interface
주로 터미널에 사용되는 명령 줄이나, 텍스트 기반의 인터페이스.
GUI
Graphical User Interface
그래픽 요소로 구성된 사용자 인터페이스. 우리가 만드는 게임 UI는 전부 이쪽!

좋은 UI가 되려면?

01
직관성 ( Intuitiveness )
고민 / 생각하지 않아도 쉽게 인지할 수 있도록. 익숙한 디자인 패턴으로 학습 부담을 줄여요.
버튼 · 메뉴 · 옵션이 명확하게 구분되도록.
02
일관성 ( Consistency )
미적 요소 / 기능적 요소 모두 포함. 동일 기능은 동일 외형과 동작으로 유지해요. 예: 모든 팝업의 닫기 버튼은 같은 위치에.
03
효율성 ( Efficiency )
자주 하는 행동은 빠르게. 단, 아이템 삭제처럼 되돌리기 어려운 행동에는 확인 단계가 필요해요.
04
반응성 ( Responsiveness )
살아있는 UI ( 피드백 ). 눌렀을 때 반응을 알 수 있어야 해요. 예: 구매 중 표시 → 완료 안내.

어포던스 vs 넛지

AFFORDANCE
형태 자체가 행동을 가능하게 만든다
(선택지를 바꾸지 않음)
NUDGE
배치 · 기본값으로 선택을 유도한다
(물리적 가능성은 그대로)

PART 3 · 기획

UX도 살펴볼까요?

User Experience — UI보다 훨씬 더 큰 그림이에요.

UX, 란?

UXUser Experience
사용자가 게임을 접하고 이용하며 느끼는 생각 · 감정 · 반응을 포함한 전체 경험.
작은 의미
UI에 연계된 UX
UI를 쓰면서 바로 느끼는 경험.
버튼의 반응, 메뉴 전환 속도와 구성, 피드백의 즉각성처럼 상호작용 하나하나의 손맛.
큰 의미
게임 전체의 UX
게임을 알게 되고, 배우고, 플레이하고, 다시 돌아오기까지의 모든 경험.
스토리 · 밸런스 · 성장 · 안정성 등 UI 사용 경험을 포함한 전체 경험.
예: 보상 버튼은 편해도, 보상이 불공정하면 전체 경험은 나쁠 수 있어요.

좋은 UX를, 왜 만들어야 할까요?

01
유저 이탈 방지
좋은 경험은, 유저가 게임을 떠나는 걸 막아줘요.
02
긍정적 입소문
유저들로부터, 긍정적인 피드백을 만들어내요.
03
복귀 여지
한번 이탈한 유저에게도, 돌아올 여지를 만들어내요.
💰
결국, 수익 창출의 기반이 돼요.

부정적인 UX 가 게임에 영향을 주는 과정.

좋은 UX 를 구성하려면 어떻게 해야 할까요?

03 · 게임에 녹아드는 것들이어야 하겠죠?
⚡
피드백이 필요해요
직관적인 인지가 가능하게 말이에요.
명중과 빗나감은 쉽게 구분할 수 있어야 해요.
시각 · 청각 · 진동으로 정보를 보완해요.
💡
의미를 부여해볼까요?
열쇠를 주웠다라는 이벤트에서,
열쇠는 그냥 전리품이 아니라,
문을 열 수 있다는 역할이 부여되면 좋아요.
왜?라는 질문을 항상 고민해봐요.
📖
규칙과 맥락에 연결해요
행동이 게임의 규칙 · 목표 · 맥락과 이어져야 해요. 이야기는 그 연결을 만드는 방법 중 하나예요.
예시
마지막 포션으로 동료를 살렸다 → 동료가 다음 전투에서 도움을 준다.
선택 → 결과 → 다음 선택의 변화가 이어지면, 행동의 의미를 경험할 수 있어요.

목표를 이해하고, 다음 행동을 고를 수 있나요?

경험 점검 ① · 이해와 방향
🧭
지금 무엇을 해야 하나요?
현재 목표와 중요한 정보를 구별할 수 있어야 해요. 긴 설명을 외우게 하기보다, 필요한 순간에 알려줘요.
💡
왜 해야 하는지 아나요?
행동의 목적과 기대할 결과를 이해할 수 있어야 해요. 이유 없는 지시보다, 선택할 근거를 제공해요.
🪜
처음 해도 배울 수 있나요?
한 번에 모든 규칙을 가르치기보다, 해보면서 익히게 해요. 익숙한 사람은 설명을 건너뛸 수 있게요.
퀘스트 예시
“재료 3개 수집”만 표시 → 누구를 위해 필요한지, 어디서 찾는지, 진행이 얼마나 됐는지 알려줘요.
다 알려주는 것만이 답은 아니에요. 탐험 게임이라면 발견할 단서를 주는 방식도 있어요.

실패해도, 납득하고 다시 시도할 수 있나요?

경험 점검 ② · 실패와 공정함
🔎
왜 실패했는지 알 수 있나요?
피격이나 실패 원인을 알아차릴 수 있어야 해요. 공격 전조와 결과가 읽혀야, 운이 아니라 학습으로 느껴져요.
🔁
다르게 시도할 여지가 있나요?
실패에서 얻은 정보로 다음 전략을 바꿀 수 있어야 해요. 도전과 무관한 긴 재이동은 다시 시도할 의지를 꺾을 수 있어요.
⚖️
규칙이 일관되게 적용되나요?
안내한 판정과 실제 결과, 위험과 보상이 납득돼야 해요. 공정함은 모두에게 똑같은 결과를 주는 것과는 달라요.
보스전 예시
예고 없이 즉사 → 공격 전조와 피격 원인을 보여주고, 다음에는 회피 시점을 바꿔볼 수 있게 해요.
좋은 UX = 쉬운 게임은 아니에요. 어려워도 이유를 이해하고 개선할 수 있는 경험을 만들어요.

기다리고 반복하는 시간도 설계했나요?

경험 점검 ③ · 시간과 반복
⏳
기다림을 이해할 수 있나요?
로딩이나 매칭 중에는 진행 상태와 가능한 행동을 알려줘요. 시간 예측이 어렵다면, 근거 없는 남은 시간을 보여주지 않아요.
🗺️
이동에도 경험이 있나요?
이동 중 발견 · 선택 · 휴식을 줄 수 있어요. 이미 충분히 경험한 구간은 빠른 이동이나 건너뛰기를 검토해요.
🌱
반복 속에 변화가 있나요?
같은 전투라도 전략 · 숙련 · 보상이 달라질 수 있어요. 의미 없이 같은 입력만 반복하게 만드는 건 아닌지 살펴봐요.
반복 플레이 예시
같은 일일 임무를 매번 같은 순서로 진행 → 경로 · 목표 · 전략의 선택을 주거나, 익숙한 준비 절차를 줄여요.
모든 시간을 짧게 만들기보다, 의도한 긴장과 휴식은 살리고 불필요한 마찰을 줄여요.

좋은 UX 를 구성하려면 어떻게 해야 할까요?

04 · 테스트와, 완성도를 챙겨요.
① 기준 생성 / 수정
먼저 기준부터 정해요.
모든 것들은 이 기준으로부터 파생되는 구조로요.

그럼에도 불구하고 문제는 생겨요.

그럴 땐, 트리아제를 써볼까요?

원인 종류는 아래처럼 분류하고, 우선순위는 진행 차단 · 발생 빈도 · 영향 범위로 판단해요.
기술 · 접속과 안정성
접속 실패 · 비정상 종료 · 멈춤.
예: 많은 사용자가 접속하지 못한다면, 진행을 막는 문제부터 해결해요.
조작 · 반응과 피드백
기대하지 않은 결과가 생기거나, 긴 로딩, 프레임 드랍, 렉으로 조작이 정확히 반영 안 되는 경우도 있어요.
아주 불쾌한 경험을 만드는 요소들이에요.
기획 · 이해와 진행
정리되지 않은 직관적이지 않고 복잡하기만 한 UI.
규칙이나 다음 목표를 이해하기 어려운 상호작용.
지나치게 복잡한 조작 방식.
밸런스 · 도전과 공정함
너무 어렵거나 너무 쉬운 난이도.
P vs. P · 보상의 불공정함. 도전 의식 없는 무난한 구성.
보상 손실처럼 피해가 크면 이 문제도 높은 우선순위가 돼요.
함께 판단해봐요: 접속 불가 / 보상 설명 오해 / 장식 애니메이션 끊김 — 무엇부터, 왜 고칠까요?

Canvas — Render Mode

World Space
게임 월드 안의 한 지점에 놓인 UI. 카메라와의 거리 · 각도에 따라 크기와 방향이 달라져요. RectTransform으로 월드 위치와 UI 크기를 조절해요.

예: 머리 위 체력 바 · NPC 이름표 · 월드 속 안내판.
Screen Space
Overlay는 화면 맨 위에 항상 그려지고, 카메라 설정의 영향을 안 받아요(가장 흔히 씀). Camera는 지정한 카메라 안쪽에 그려져, 렌더링 설정에 따라 3D 오브젝트와 함께 표현할 수 있어요.

예: HUD · 메뉴 · 팝업.
Ex.
게임에서는 한 가지만을 사용하는 게 아니라, 다양한 오브젝트의 특성에 따라 섞어서 사용해요.
HUD · MENU 등은 Screen Space-Overlay, 적 머리 위 데미지 숫자나 이름표 같은 Name Tag는 World Space로.
새 Canvas를 만들면 기본값은 Screen Space - Overlay예요.
모두 Canvas 컴포넌트의 Render Mode 옵션이에요. UI 배치에는 똑같이 RectTransform을 써요.

Canvas Scaler

Canvas Scaler
해상도 · 화면 크기가 다른 기기에서도, UI 크기를 일관되게 유지해주는 컴포넌트.
Constant Pixel Size
Scale Factor 기준으로 픽셀 크기를 유지해요. 해상도가 커지면 화면에서 차지하는 비율은 작아져요.

언제? 에디터 툴처럼, 해상도와 무관하게 항상 같은 크기가 필요할 때.
Scale with Screen Size
Reference Resolution 기준으로 배율을 조절해요. Match로 가로 / 세로 중 무엇을 더 따를지 정해요.

언제? 대부분의 모바일 게임이 이 모드를 써요.
Constant Physical Size
DPI를 이용해 mm 등 물리 단위 크기를 유지해요. 기기의 DPI 정보가 정확해야 해요.

언제? 거의 안 써요 — DPI 보고가 부정확한 기기가 많아요.
실습 시작값: Scale with Screen Size · Reference Resolution 1920 × 1080 · Match 0.5. 비율을 바꾸며 결과를 비교해요.

EventSystem — 입력을 UI의 행동으로

Canvas가 UI를 보이게 한다면, EventSystem과 입력 모듈은 UI를 조작할 수 있게 해요.
선택과 처리의 중심
EventSystem
현재 선택된 UI를 관리하고, 활성 입력 모듈의 처리를 진행해요.

예: 키보드로 이동했을 때 어떤 버튼이 선택돼 있는가?
일반적인 단일 사용자 씬에서는 보통 하나를 둬요.
입력을 이벤트로 해석
Input Module
마우스 · 터치 · 이동 / 확인 입력을 읽어 UI 이벤트로 바꿔요.

포인터 입력이면 Raycaster로 대상을 찾고, 누름 · 뗌 등 이벤트를 전달해요.
사용하는 입력 시스템에 맞는 모듈이 필요해요.
이벤트에 반응
Button
선택 · 눌림 상태를 표시하고, 클릭이나 확인 입력 조건이 맞으면 OnClick을 실행해요.

OnClick에 설정 창 열기 함수를 연결해야 실제 창이 열려요.
같은 설정 버튼, 두 가지 조작
마우스: 버튼 위에서 누르고 놓기 → 클릭 판정 → 설정 창 열기.
키보드 / 게임패드: 설정 버튼 선택 → 확인 입력(Submit) → 설정 창 열기.
EventSystem이 게임의 모든 입력을 담당하는 것은 아니에요. 여기서는 uGUI 입력 처리를 이야기해요.

Graphic Raycaster — 지금 무엇을 눌렀나요?

입력 모듈이 요청하면, 해당 Canvas에서 포인터 위치와 겹치는 UI 후보를 찾아요. 함수 실행은 Button의 역할이에요.
보이는 것과 클릭되는 것은 달라요
① 어떤 UI를 찾을까요?
Image · Text 등 Graphic의 영역과 Raycast Target, 마스크 · CanvasGroup 등의 조건을 검사해요. 입력 모듈은 정렬된 탐색 결과로 이벤트 대상을 정해요.
② 투명 패널을 어떻게 할까요?
장식용: Raycast Target을 꺼서 뒤 버튼을 누르게 해요.
모달 배경: 켜서 뒤 화면 입력을 막고, 닫기 등 필요한 동작을 연결해요. 이미지의 투명도만으로 결정되지 않아요.
버튼이 안 눌린다면?
입력 모듈 → UI 탐색 → 입력 차단 → OnClick 연결 순서로 확인해요. 클릭해서 점검표 보기

“버튼이 안 눌려요!” 점검표

① 입력이 들어오나요?

활성 EventSystem과 입력 방식에 맞는 Input Module, 연결된 UI 입력 액션을 확인해요.

② 대상을 찾을 수 있나요?

Canvas의 Graphic Raycaster와 버튼 Graphic의 Raycast Target이 켜져 있는지 확인해요.

③ 다른 UI가 막고 있나요?

앞의 투명 패널, Button의 Interactable, 부모 CanvasGroup의 Interactable · Blocks Raycasts를 살펴봐요.

④ 실행할 함수가 있나요?

Button의 OnClick에 대상 오브젝트와 올바른 함수를 연결했는지 확인해요.

다시 클릭하면 닫혀요.

RectTransform — 어디를 기준으로 놓을까요?

uGUI의 사각형 배치 도구예요. Anchor는 부모 기준, Pivot은 자기 기준으로 생각하면 쉬워요.
예: 화면 우상단에서 24만큼 떨어진 닫기 버튼
Anchors · 부모의 어느 지점?
Min = Max = (1, 1)은 부모 우상단이에요.
부모 크기가 바뀌면 기준점도 따라 움직여요.
Pivot · 내 사각형의 어느 지점?
(1, 1)은 내 우상단, (0.5, 0.5)는 중앙이에요.
위치 · 회전 · 확대 / 축소의 기준점이에요.
Position · 기준에서 얼마나 떨어질까요?
이 예에서는 (−24, −24)로 왼쪽 · 아래로 이동해요.
Width / Height는 버튼 자체의 크기예요.
고정 배치와 Stretch를 구분해요
닫기 버튼: 우상단 Anchor + 위치 차이 + Width / Height. 배경 패널: Anchors를 벌려 Stretch + Left / Right / Top / Bottom 여백.
Anchor Presets는 이런 배치를 고르는 메뉴예요. Alt는 위치도, Shift는 Pivot도 함께 맞춰요.

Sprite Atlas — 그림은 따로 쓰고, 텍스처는 함께

여러 스프라이트를 하나 이상의 Atlas 텍스처에 패킹해요. 버튼과 아이콘은 여전히 각각의 Sprite로 참조해요.
원리: 여러 이미지 → Atlas 안의 각 영역
클릭해서 실제 Atlas 예시 보기
어떤 효과? · 텍스처 공유
같은 텍스처를 쓰면 여러 UI의 그리기를 묶기 쉬워져요. 그리기 명령(드로우 콜)을 줄일 수 있어요.
머티리얼 · 마스크 · 그리기 순서 등 다른 조건도 맞아야 해요.
어떻게 묶을까요? · 함께 쓰는 화면 단위
로비 · 전투 HUD처럼 함께 쓰는 이미지끼리 묶어요.
일부 Sprite만 써도 해당 Atlas 텍스처가 메모리에 올라올 수 있어요. 무관한 이미지를 모두 몰아넣지 않아요.
직접 확인해볼까요?
Sprite Atlas 생성 → 대상 Sprite / 폴더 등록 → Pack Preview로 확인해요.
적용 전후를 Frame Debugger 등으로 비교해요. Atlas라고 무조건 1 Draw Call이 되거나 메모리가 줄지는 않아요.
